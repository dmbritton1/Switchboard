# Codex Telemetry Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps use
> checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship authoritative Codex plan and rate-limit windows—including the
five-hour usage limit—through a reusable account-scoped app-server foundation,
while all Codex sessions and turns remain owned by the existing SDK.

**Architecture:** Keep `@openai/codex-sdk` pinned to `0.145.0`, validate the
telemetry subset of the protocol generated by that exact executable, and run one
long-lived app-server supervisor per Codex account. A provider-neutral in-memory
limit model keeps window exhaustion separate from bucket/account blocking and
feeds account meters, account ranking, and Codex reset scheduling. Claude
continues using its current no-turn probe and event-based reset behavior. The
scheduler dispatches timed work first, then performs a bounded, coalesced
authoritative Codex read at a reset boundary before releasing reset work. No
app-server thread or turn method is available in this release.

**Tech Stack:** Node.js 22.18+, TypeScript executed directly by Node,
`@openai/codex-sdk` 0.145.0, newline-delimited JSON-RPC over stdio, HTTP/SSE,
browser JavaScript, `node:test`.

**Spec:**
[`docs/superpowers/specs/2026-08-11-codex-app-server-parity-design.md`](../specs/2026-08-11-codex-app-server-parity-design.md)

**Review incorporated:** 2026-08-26 pre-build protocol review. Every accepted
correction is restated in this plan so implementation does not depend on a
separate review artifact.

**Official references:** [Codex App Server](https://developers.openai.com/codex/app-server),
[Advanced Configuration](https://developers.openai.com/codex/config-advanced),
[Configuration Reference](https://developers.openai.com/codex/config-reference).
The generated contract from the pinned executable remains authoritative when
online documentation and the installed release differ.

## Scope and supersession

This plan is the complete implementation plan for phase one of the revised
design. It supersedes the first-release sequencing in:

- `docs/superpowers/plans/2026-08-11-codex-app-server-foundation.md`
- `docs/superpowers/plans/2026-08-11-codex-limits-and-cutover.md`

Do not execute either older plan before this one. They assume app-server turn
transport lands before limits and therefore no longer describe the approved
release order. Later work will revise them around the supervisor and contract
created here.

Phase one ends with:

- authoritative Codex account windows and plan names;
- a five-hour headline when Codex reports that as its shortest window;
- provider-neutral account ranking and expanded meter rows;
- one long-lived, reusable app-server process per supported Codex account;
- Codex reset-scheduled work released only after a fresh boundary read, while
  Claude retains its existing event-based reset behavior;
- an opt-in, no-turn live compatibility smoke check.

Phase one does **not** add app-server threads, turns, approvals, questions,
capability discovery, MCP sidecars, transport selection, typed
`UsageLimitExceeded` handling, or automatic recovery of an SDK-owned Codex
failure. The pinned server-request method for the later question phase is
`item/tool/requestUserInput` (not the older spec spelling
`tool/requestUserInput`); phase one only recognizes and denies it.

## Global constraints

- Implement in an isolated worktree created with
  `superpowers:using-git-worktrees`; the primary checkout currently has unrelated
  user edits that must remain untouched.
- Use Node 22.18 or newer.
- Keep `@openai/codex-sdk` pinned exactly to `0.145.0`; do not upgrade as part of
  phase one because its generated schema already contains the required methods.
- Keep every Codex session on the existing SDK adapter. Production telemetry
  code must contain no `thread/*` or `turn/*` request path.
- Keep Codex sandbox fixed to `workspace-write` and approval policy fixed to
  `never`; do not expose either setting.
- Do not write `.codex/config.toml` or mutate any user/project Codex config.
- Launch telemetry with process-local overrides for empty hooks, empty MCP
  servers, disabled OTel export, and strict config validation. If the pinned
  executable or generated contract cannot establish side-effect-free no-turn
  startup, mark telemetry unavailable and keep the local estimate.
- Never refresh auth. `account/read` must use `{ refreshToken: false }`.
- Phase one supports authoritative Codex telemetry only for managed ChatGPT
  auth. Normalize `account/read` account kinds separately from
  `account/updated` auth modes. Deny external token refresh requests and mark
  external auth telemetry unsupported with an actionable estimate-fallback
  reason.
- Never persist provider snapshots. Never log, persist, return over SSE, or
  render account environment values, raw stderr, auth data, or absolute paths.
- Keep `npm test` offline. All automated app-server tests use the fake process;
  the installed-account smoke check is a separate manual command.
- Preserve existing Claude rate-limit events and Claude automatic requeue
  behavior, including `Usage.free()` fallback. Apply fresh authoritative reset
  gating only to Codex. Do not broaden Claude's heuristic to Codex snapshots or
  SDK errors.
- Treat unsolicited non-telemetry notifications as private process traffic.
  In particular, never expose `remoteControl/status/changed` hostname or
  installation identifiers through diagnostics, Registry, SSE, or UI.
- Run focused tests after each red/green cycle and `npm test` before completion.
- Commit only files named by the active task. Do not include unrelated dirty
  files in any task commit.

- [ ] **Step 1: Write RED account-mode tests**

  Test the two protocol vocabularies separately. For `account/read`, cover the
  exact tagged values `chatgpt`, `apiKey`, `amazonBedrock`, logged-out
  `{ account: null, requiresOpenaiAuth: true }`, missing/`unknown` plan, and
  malformed results. For `account/updated`, cover all seven exact `AuthMode`
  values: `apikey`, `chatgpt`, `chatgptAuthTokens`, `headers`, `agentIdentity`,
  `personalAccessToken`, and `bedrockApiKey`.

  Managed `chatgpt` is supported. API key, Bedrock, logged-out, and external
  token/header/identity modes are unsupported with distinct stable reason
  strings. Never compare `apiKey` to `apikey`; they belong to different inputs.
  The supervisor calls:

  ```ts
  client.request('account/read', { refreshToken: false });
  ```

- [ ] **Step 2: Write RED multi-window normalization tests**

  If `rateLimitsByLimitId` contains at least one usable keyed bucket, normalize
  only that view and ignore legacy `rateLimits`; otherwise normalize the legacy
  bucket as `default`. For keyed buckets, use the map key as the normalized
  bucket ID and reject a non-null conflicting payload `limitId`. Expand windows
  into `${bucketId}:primary` and `${bucketId}:secondary`, so a nullable legacy
  `limitId` becomes `default:primary`, never `null:primary`. Use `limitName` when
  available; otherwise derive the visible label from `windowDurationMins`
  (`5h`, `7d`, or a neutral duration label).

  Normalize numeric resets through `providerTimestampMs()` because the generated
  type documents no unit. Keep nullable durations/resets nullable. Reject
  non-finite percentages, duplicate IDs, empty usable windows, and malformed
  buckets. Keep per-window `reached = usedPercent >= 100`.

  Separately normalize bucket-level `rateLimitReachedType` and
  `spendControlReached` into `blocks`. Only `rate_limit_reached` accompanied by
  reached windows with future resets is resettable. Credit depletion, workspace
  usage-limit, spend-control, or a reached window without a future reset must
  block scheduling without inventing a reset time. Do not copy a bucket-level
  block onto every window's `reached` flag: a block can occur below 100% and has
  no documented ownership of one particular window. Normalize plan literal
  `unknown` to null.
