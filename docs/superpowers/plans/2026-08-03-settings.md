# Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a settings dialog with seven preferences persisted in `state.json`, every default reproducing today's behavior exactly.

**Architecture:** A `Settings` object lives in the `Registry` beside sessions, is written through the existing coalesced save path, and rides the existing SSE snapshot to the browser. One new `settings` command validates and merges a partial patch. Four settings are read only by the browser (`account`, `branchPrefix`, `notifyOn`, `sort`, `collapseDone`); two change server behavior (`autoApprove` at create, `autoRequeue` at session death).

**Tech Stack:** Node >= 22.18 running TypeScript directly (no build step), `node --test`, vanilla ES modules in `web/`, no dependencies.

## Global Constraints

- Node 22.18+. No build step — TypeScript runs directly. Do not add a bundler.
- No new dependencies. No new state file: settings go in `state.json`.
- Run `npm test` before declaring any task complete. While iterating, run the single focused `node --test` command given in the task.
- Every setting's default must reproduce current behavior. A `state.json` with no `settings` key must behave identically to today.
- Tests stay hermetic: no network, no real accounts, no paid model turns. Use `new Registry('/dev/null')` or a temp dir, per the existing patterns in `test/sessions.test.ts`.
- Account `env` values are launch-only secrets: never persist, log, return over SSE, or render them. Settings must not touch `accounts.json`.
- Do not broaden the Codex sandbox (`workspace-write`) or approval policy (`never`), and do not add either to the settings dialog — `AGENTS.md` names both a safety boundary.
- Follow the house comment style: explain *why* a non-obvious line exists, in prose, above it.

```ts
/**
 * Coerces a parsed `settings` value into a real Settings, key by key.
 *
 * state.json is hand-editable and can also be written by a newer build than
 * the one reading it, so every key is validated individually and a bad one
 * falls back to its default rather than poisoning the whole block. Unknown
 * keys are dropped by construction: the output is built from the defaults, not
 * spread from the input.
 */
function coerceSettings(raw: unknown): Settings {
  const out = { ...DEFAULT_SETTINGS };
  if (!raw || typeof raw !== 'object') return out;
  const r = raw as Record<string, unknown>;
  if (typeof r.autoApprove === 'boolean') out.autoApprove = r.autoApprove;
  if (typeof r.collapseDone === 'boolean') out.collapseDone = r.collapseDone;
  if (typeof r.autoRequeue === 'boolean') out.autoRequeue = r.autoRequeue;
  if (typeof r.branchPrefix === 'string') out.branchPrefix = r.branchPrefix;
  if (r.account === null || typeof r.account === 'string') out.account = r.account;
  if (r.sort === 'blocked' || r.sort === 'newest' || r.sort === 'account') out.sort = r.sort;
  if (Array.isArray(r.notifyOn)) {
    const valid = r.notifyOn.filter(
      (v): v is NotifyOn => v === 'needs-you' || v === 'done' || v === 'error',
    );
    // An array that is present but has nothing valid in it means "notify me
    // about nothing", which is a legitimate choice — so an empty result is
    // kept, unlike a non-array which is a shape error and falls back.
    out.notifyOn = valid;
  }
  return out;
}
```

```ts
const SORTS = ['blocked', 'newest', 'account'] as const;
const NOTIFY = ['needs-you', 'done', 'error'] as const;

/**
 * Validates a settings patch before it reaches the Registry.
 *
 * Strict where `coerceSettings` (sessions.ts) is tolerant, and deliberately so:
 * that one reads a file this app wrote, while this reads an unauthenticated
 * localhost POST that now changes how agents launch. An unknown key here is an
 * error rather than a silent drop, so a client sending `sandboxMode` learns it
 * was ignored instead of believing it took effect.
 */
export function parseSettingsPatch(body: unknown): { patch: Partial<Settings> } | { error: string } {
  if (!body || typeof body !== 'object' || Array.isArray(body)) {
    return { error: 'patch must be an object' };
  }
  const patch: Partial<Settings> = {};
  for (const [key, value] of Object.entries(body as Record<string, unknown>)) {
    switch (key) {
      case 'autoApprove': case 'collapseDone': case 'autoRequeue':
        if (typeof value !== 'boolean') return { error: `${key} must be a boolean` };
        patch[key] = value;
        break;
      case 'branchPrefix':
        if (typeof value !== 'string') return { error: 'branchPrefix must be a string' };
        patch.branchPrefix = value;
        break;
      case 'account':
        // Not checked against the account list: an account can be removed from
        // accounts.json while a stale pin names it, and rejecting the patch
        // would make settings unsavable until the user noticed. The New dialog
        // falls back to freest when the pinned name is not in the list.
        if (value !== null && typeof value !== 'string') {
          return { error: 'account must be a string or null' };
        }
        patch.account = value;
        break;
      case 'sort':
        if (!SORTS.includes(value as SortMode)) {
          return { error: `sort must be one of: ${SORTS.join(', ')}` };
        }
        patch.sort = value as SortMode;
        break;
      case 'notifyOn':
        if (!Array.isArray(value) || value.some((v) => !NOTIFY.includes(v as NotifyOn))) {
          return { error: `notifyOn must contain only: ${NOTIFY.join(', ')}` };
        }
        patch.notifyOn = value as NotifyOn[];
        break;
      default:
        return { error: `unknown setting: ${key}` };
    }
  }
  return { patch };
}
```

```js
 * Grid order. `blocked` is the default and the original behavior: blocked
 * first, then running, then finished, most recently changed first within each.
 * `newest` is a flat recency list. `account` groups by account name and falls
 * back to `blocked` inside each group, so grouping never costs you the
 * blocked-first reflex within the account you are looking at.
 */
export function sortSessions(sessions, mode = 'blocked') {
  const cmp = mode === 'newest'
    ? (a, b) => b.statusSince - a.statusSince
    : mode === 'account'
      ? (a, b) => a.account.localeCompare(b.account) || byBlocked(a, b)
      : byBlocked;
  return [...sessions].sort(cmp);
}

/** Hides finished sessions when the setting asks. `stopped` is deliberately not
 *  hidden: it carries a Resume button and unfinished work, unlike `done`. */
export function visibleSessions(sessions, collapseDone) {
  return collapseDone ? sessions.filter((s) => s.status !== 'done') : sessions;
}
```

```js
/**
 * Which sessions just entered a status worth notifying about.
 *
 * Keyed `id:status` rather than by id alone, so needs-you and done are tracked
 * independently and a session that goes needs-you -> working -> needs-you
 * notifies twice, which is two real interruptions.
 *
 * `seed` exists for one reason: EventSource reconnects on its own and the
 * server pushes a full snapshot on connect. Called with seed=true on the first
 * payload after a connect, this fires nothing and returns a seen-set covering
 * everything already on the board — without it, every dropped connection
 * notifies once per finished session for work that ended hours ago.
 *
 * The returned set is rebuilt from the current sessions each call, so a
 * deleted session's keys do not accumulate forever.
 */
export function newlyNotifiable(sessions, notifyOn, seen, seed = false) {
  const watched = sessions.filter((s) => notifyOn.includes(s.status));
  const next = new Set(watched.map((s) => `${s.id}:${s.status}`));
  const fire = seed ? [] : watched.filter((s) => !seen.has(`${s.id}:${s.status}`));
  return { fire, seen: next };
}
```
